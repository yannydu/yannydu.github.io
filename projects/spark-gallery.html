Spark Gallery

A published gallery of summer camp work, built so no child's real name ever reaches the cloud.

What it is

Every week of camp produces photos, code projects, and videos. Spark Gallery turns that week into a published issue families can open from a link, with each camper getting their own page. Instructors upload from the camp room as the week runs, and I pull each camp in when it finishes and publish. Live since summer 2026, it now holds 13 camps and 471 camper pages.

Constraints

A privacy ruling meant children's real names could not sit on the cloud provider in any form, not even for the days between upload and publish. Instructors are camp staff, so the upload path had to be a link and a printed sheet. Families needed to browse without an account.

Architecture

 instructors                families
     |                          |
     v                          v
[ upload Worker ]        [ gallery site ]
 separate origin,         Astro on Workers
 no shared cookies        D1 index + media
     |                          ^
     v                          |
 private inbox  --intake-->  publish
 UUID folders,    (on my       build
 handles only     machine)

The upload tool runs from its own Worker origin, so a session there never shares cookies with the public gallery. Real names stay on my machine and on paper; what travels is a folder named by a random identifier and a friendly pseudonym.

Decisions I made

  • Pseudonyms are assigned locally before camp starts, so the upload path never receives a name it would have to strip.
  • A pre-push git hook fails closed when a real name appears in files headed for the repository. It stops the push rather than warning.
  • Video is re-muxed through ffmpeg before publishing, which drops the location and device metadata phones attach. CI installs ffmpeg so that step stays tested.
  • gitleaks scans the full history on every CI run, not only the newest changes.
  • Test publishes go to a separate sandbox environment, so invented data can never land beside a real camp.
  • 51 test files run under the Node test runner, including the privacy guards.

What I decided not to build

No accounts, for campers or for families. An account would mean holding family contact details and a password reset path year round, for a site that matters a few weeks each summer. A link and a pseudonym cover what families want, which is seeing their kid's work. No program tool I build gives a child a login.
