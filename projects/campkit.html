Campkit

The internal platform where our camp curriculum is written, assembled, and costed.

What it is

Campkit is where our camp curriculum is written, assembled into camps, and prepared for class. Writers author an activity once and arrange published activities into days; the site produces the reading view, the print packet, and a shopping list costed from the student count. It replaced one large Word document per camp, with draft copies spread across OneDrive and supply names typed by hand: white paper, printer paper, paper. The activity templates follow SPARK, a standard structure I created so quality stays consistent between writers.

Dev log

Oct 11 to Oct 13, 2026: one editor by default

On Oct 11 the guided writer became the single editor: opening an activity went to it, with a Basics step for title, grades, duration and tags first. On Oct 13 activities started opening in the one-page editor instead. The guided writer stayed, as Guided writer in the More menu.

Sep 25, 2026: weekly manual deploys

Merges to main stopped deploying. Production, code and database migrations together, now updates when someone runs the Deploy workflow, usually on Fridays. A manual run was chosen over a schedule so migrations never apply unwatched. Each deploy is named by its date and gets a GitHub Release listing the merged pull requests. The footer shows the same name, so a bug report pins an exact deploy.

Sep 22 to Sep 25, 2026: a prep dashboard

I wanted instructors to have a better landing page, where they see what they need to do at a glance. Instructors mark each activity they teach as not started, in progress or prepped, and the prep dashboard shows that as a grid per camp, opening on an overview with one row per instructor and program. Instructor notes gained edit, delete, step pins and printing.

Sep 15, 2026: a rich-text editor

I wanted curriculum writers to be able to format their text better. Text fields now open in Toast UI Editor, a WYSIWYG (what you see is what you get) editor with a formatting toolbar. Each field is still stored as Markdown.

Sep 10, 2026: an API

I wanted better AI integration for my own workflows. The API (application programming interface) at /api/v1 lets a script work with programs and activities and upload files, signed in with a Cloudflare Access service token instead of a person’s login. It is rate limited per caller, at 600 requests a minute, so one runaway script cannot flood it.

Aug 14, 2026: Day Board v3

With a five-day camp and a full library, dragging a card in meant scrolling the page. Day Board v3 docks the library as a shelf under the board and fits it all on one screen: each day scrolls its own list, and five days fit side by side.

Jul 6, 2026: drag and drop, and an importer

The first builder had only an Add activity button, which made moving activities around hard, so the board became drag and drop. I also wrote an importer from the Typst curriculum; by Jul 5 it had brought in the Summer 2026 programs: 175 activities, 10 camps and 143 supplies.

Jul 1, 2026: the first app, in a day

Word fought me on our tech curriculum: no code blocks, no repeatable template. I moved it to Typst, a typesetting language. That pipeline compiled 355 files in CI (continuous integration) on every push, with a small web editor so staff never touched git. The science writers stayed on Word, and summer camps showed the supply-list mess. In one day I built the first Campkit: authoring, a camp builder, supplies, the print packet and a costed shopping list.

Constraints

Built for about ten writers and twenty instructors, with no budget and no appetite for another password. Past camps have to stay as they ran, even after their activities are edited for next year.

Architecture

Platform-specific calls sit behind a single module, so a later move to university servers rewrites that module, not the app.

Decisions I made

  • Publishing freezes a copy of the activity, and camps point at that copy, so an edit never rewrites a camp that already ran.
  • Materials come from one catalogue with alias matching and a single unit per item, so “rubber band” and “elastic band” cannot drift apart. Free-text supply names are impossible to type.
  • Staff sign in through Cloudflare Access with a one-time PIN sent to their email, and the app never sees a password. Roles are granted by invite, never on first arrival.
  • Every change passes typecheck, lint and a 62-file Vitest suite before it merges. Since Oct 11 those checks run on my laptop instead of GitHub Actions, because our free plan’s 2,000 monthly minutes were running out.

One habit came from a mistake next door. A strategy PDF reached a funder four hours behind its Markdown source and still had a grade band we had already changed. A pre-commit hook now blocks a source change committed without its regenerated render.

What I decided not to build

A family portal beside registration, with saved child profiles and parent logins. I shelved it in writing: it would have turned a seasonal sign-up into a year-round store of children’s personal information, with its own login and a retention policy someone must enforce. The program uses a stock self-hosted ticketing tool instead.
