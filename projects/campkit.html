Campkit

The internal platform where our camp curriculum is written, assembled, and costed.

How it was built: I frame the problem and make the architecture and privacy decisions; Claude Code writes much of the code.

Milestones

  • Nov 6, 2026 Problem: no one place to see what is happening when. Fix: events group programs; runs hold the dates, room and instructors. Result: an events calendar with a campus filter and search, and each run marked Ready or Not ready.
  • Nov 3, 2026 Problem: instructors needed to plan lessons in the team’s familiar format. Fix: lesson delivery plans that fill in the boxes of the team’s Word template. Result: a lesson reaches Prepped only when its plan is finished.

What it is

Campkit is where our camp curriculum is written, assembled into camps, and prepared for class. Writers author an activity once and arrange published activities into days; the site produces the reading view, the print packet, and a shopping list costed from the student count. It replaced one large Word document per camp, with draft copies spread across OneDrive and supply names typed by hand: white paper, printer paper, paper. The activity templates follow SPARK, a standard structure I created so quality stays consistent between writers.

Dev log

Nov 6 to Nov 12, 2026: events and runs

Problem
I wanted one place to see what is happening when.
Changed
An event is a named date range at a campus or venue that groups programs, such as a camp week or a club season. A run is one outing of a program inside an event, with its own room and two instructors; runs now hold the dates and the packing lists. The programs list groups under events, and the admin home page became a month calendar of events.
Result
A run is Ready when its dates and room are set, it has enough instructors, and everything is packed; lesson plans no longer count. Instructors see only the runs of published programs on the new events calendar, which has a campus filter and search.

Nov 3 to Nov 6, 2026: lesson delivery plans

Problem
I wanted instructors to plan each camp lesson in the format the team was used to.
Changed
Each camp lesson has a lesson delivery plan filling in the boxes of the team’s Word template. A lead can comment on each step, mark it reviewed, and print it in the template’s layout from the browser; Prep was renamed Lesson plans in the menu.
Result
An instructor’s lesson reaches Prepped only when the plan is finished. On Nov 13 leads could print every plan at once or one event’s, each on a fresh sheet, so a double-sided stack splits cleanly into one handout per instructor.

Sep 25, 2026: weekly manual deploys

Changed
Merges to main stopped deploying; production, code and database migrations together, now updates when someone runs the Deploy workflow, usually on Fridays. A manual run was chosen over a schedule so migrations never apply unwatched.
Result
Each deploy is named by its date and gets a GitHub Release listing the merged pull requests. The footer shows the same name, so a bug report pins an exact deploy.

Sep 22 to Sep 25, 2026: a prep dashboard

Problem
I wanted instructors to have a better landing page, where they see what they need to do at a glance.
Changed
Instructors mark each activity they teach as not started, in progress or prepped; the prep dashboard shows that as a grid per camp, opening on an overview with one row per instructor and program. Instructor notes gained edit, delete, step pins and printing.

Sep 15, 2026: a rich-text editor

Problem
I wanted curriculum writers to be able to format their text better.
Changed
Text fields now open in Toast UI Editor, a WYSIWYG (what you see is what you get) editor with a formatting toolbar. Each field is still stored as Markdown.

Sep 10, 2026: an API

Problem
I wanted better AI integration for my own workflows.
Changed
The API (application programming interface) at /api/v1 lets a script work with programs and activities and upload files, signed in with a Cloudflare Access service token instead of a person’s login. It is rate limited per caller, at 600 requests a minute.
Result
One runaway script cannot flood it.

Aug 14, 2026: Day Board v3

Problem
With a five-day camp and a full library, dragging a card in meant scrolling the page.
Changed
Day Board v3 docks the library as a shelf under the board, and each day scrolls its own list.
Result
It all fits on one screen, with five days side by side.

Jul 6, 2026: drag and drop, and an importer

Problem
The first builder had only an Add activity button, which made moving activities around hard.
Changed
The board became drag and drop. An importer from the Typst curriculum followed.
Result
By Jul 5 the importer had brought in the Summer 2026 programs: 175 activities, 10 camps and 143 supplies.

Jul 1, 2026: the first app, in a day

Problem
Word fought me on our tech curriculum: no code blocks, no repeatable template.
Tried
I moved it to Typst, a typesetting language, compiling 355 files in CI (continuous integration) on every push, with a small web editor so staff never touched git. The science writers stayed on Word, and summer camps showed the supply-list mess.
Changed
The first Campkit went up in one day, with Claude Code writing much of the code: authoring, a camp builder, supplies, the print packet and a costed shopping list.

Constraints

Designed for about ten writers and twenty instructors (design capacity; six writers use it so far), with no budget and no appetite for another password. Past camps have to stay as they ran, even after their activities are edited for next year.

Architecture

Platform-specific calls sit behind a single module, so a later move to university servers rewrites that module, not the app.

Decisions I made

  • Publishing freezes a copy of the activity, and camps point at that copy, so an edit never rewrites a camp that already ran.
  • Materials come from one catalogue with alias matching and a single unit per item, so “rubber band” and “elastic band” cannot drift apart. Free-text supply names are impossible to type.
  • Staff sign in through Cloudflare Access with a one-time PIN sent to their email, and the app never sees a password. Roles are granted by invite, never on first arrival.
  • Every change passes typecheck, lint and a 62-file Vitest suite before it merges. Since Oct 11 those checks run on my laptop instead of GitHub Actions, because our free plan’s 2,000 monthly minutes were running out.

One habit came from a mistake next door. A strategy PDF reached a funder four hours behind its Markdown source and still had a grade band we had already changed. A pre-commit hook now blocks a source change committed without its regenerated render.

What I decided not to build

A family portal beside registration, with saved child profiles and parent logins. I shelved it in writing: it would have turned a seasonal sign-up into a year-round store of children’s personal information, with its own login and a retention policy someone must enforce. The program uses a stock self-hosted ticketing tool instead.
