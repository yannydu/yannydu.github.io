Hello Wattson

Lessons and coding tools for classrooms, opened by an access code in class, with logins coming for our own clubs.

How it was built: I frame the problem and make the architecture and privacy decisions; Claude Code writes much of the code.

Milestones

  • Nov 10, 2026 Problem: a full class pressing Verify together had to wait. Fix: four compiles at once and one build folder per library set. Result: on staging, 30 compiles started in the same second all finished, the slowest plain sketch in under 7 seconds.
  • Nov 6, 2026 Problem: students pasted lesson code instead of working through it. Fix: lesson code can’t be copied, and new lines are highlighted instead of marked with a +. Result: students were typing the code.
  • Oct 18, 2026 Problem: school laptops can’t install the Arduino IDE. Fix: the IDE’s Verify and Upload buttons in the browser, with a server compile queue and Web Serial flashing. Result: Gadget Club’s first session used it on Oct 24.
  • Jul 10, 2026 Problem: our plan called for auto-graded quizzes, interactive lesson widgets and a public catalogue. Fix: a move from Eleventy to Astro 6, keeping every URL. Result: a teacher outside our program can preview a module and run it on their own schedule.

What it is

Hello Wattson is where we publish our teaching material: 22 programs of Arduino, web development, LEGO SPIKE and Python lessons, plus the coding tools students use beside them. A teacher anywhere can browse the public catalogue, then unlock the lessons with an access code they hand to the class. For classroom students the site stores nothing: no accounts, no names, and no saved work on our side. Our own clubs are moving to logins, so we control who gets into each club and members can save their work and take it home. Over 2026 it went from a static notes site, to coding tools in the browser, to a picture-book format with our mascots.

Dev log

Nov 10 to Nov 12, 2026: faster Arduino compiles

Problem
With one compile at a time, a full class pressing Verify together had to wait.
Tried
One attempt to speed things up made compiles slower when measured, so it was reverted.
Changed
The compile container now runs four compiles at once. It also keeps one build folder per set of libraries a sketch uses, so the compiler stops rebuilding libraries it already built.
Result
On staging, 30 compiles started in the same second all finished, the slowest plain sketch in under 7 seconds. The first compile after a restart took under 3 seconds.

Nov 7, 2026: club levels and archive dates

Changed
Club seasons became levels, such as Pixel Club Level 1, and one table maps every old address to its new one. An ended club stays open to its members until an archive date set ahead of time, and the build fails if a club is missing that date.
Result
Old links still work, and kids can go back and reread their sessions after a club ends.

Nov 6 to Nov 10, 2026: lesson code you type, not paste

Problem
Instructors noticed students pasting lesson code instead of working through it.
Changed
Lesson code has no Copy button and can’t be selected or copied; a writer can turn copying back on for one block, such as a long starter file. Step-by-step code cards now highlight new lines in yellow instead of marking them with a +.
Result
Students were typing the code. They also typed the + that marked each new line, which is why the sign is gone.

Oct 31, 2026: three doors

Problem
During the summer camps I noticed the home page getting cluttered once we also offered classroom workshops and camps. I wanted it to be clearer.
Changed
The program board became three doors, Clubs, Camps and Workshops, each opening its own page and showing what is running now, or else what is coming next. Every listed program names its format and pathway; the build fails without a start date or grade band.

Oct 22 to Nov 1, 2026: a picture-book session format

Problem
I wanted the site to have a design of its own, with more of the Science Alive mascots in it, giving them more life and stories.
Changed
Each club session now opens with a story and a mission card, and idea decks carry concept pictures: small drawings of pins, parts and direction, most of them short animations with a still version. Sessions moved to this format one at a time.

Oct 18 to Oct 24, 2026: Arduino in the browser

Problem
Once the LiveCodes playground was part of the site, we wanted the same consistency for hardware, and an easier way to run hardware workshops in schools, offsite and on other devices. School laptops can’t install the Arduino IDE (integrated development environment).
Changed
It was built Oct 18 to 21: an editor that uses the IDE’s own Verify and Upload buttons. Verify sends the sketch to a compile route that needs an unlocked session and is rate-limited per IP address; a Durable Object holds up to 30 waiting compiles in front of a container running arduino-cli with internet off, and accepts only a short list of libraries. Upload flashes the board over Web Serial with our own uploader, so the editor needs Chrome or Edge. Common compiler errors come back as one plain line naming the line number, with the raw text folded underneath.
Result
As of Oct 21 one instance compiled sketches one at a time, so 25 compiles sent at once on staging waited at most 44 seconds. Gadget Club’s first session used it on Oct 24, and since Nov 12 the container runs four at once.
Still open
Flash tests on the Windows club laptop and a Chromebook. Only Linux has passed, on a real Uno.

Oct 15 to Oct 18, 2026: idea cards, playground first

Changed
Pixel Club and Gadget Club are weekly Saturday clubs whose sessions open on their own dates. Their reading pages became idea-card decks: one card at a time, with Back and Next, each card at most 40 words.
Our lead picked this layout, “One idea at a time”, from several versions.
The software clubs went playground-first: lesson steps no longer mention a local editor, and taking the project home moved to a section at the end of the lesson.

Oct 7, 2026: the Workbench

Changed
The Workbench puts the playground beside a Pixel Club lesson. On screens 1200 pixels wide and up, the lesson takes 42% of the width and the playground the rest.
Smaller screens keep a link out to the playground, and phones get no embed. If the embed hasn’t loaded in 8 seconds, the page shows a plain message and the link instead.

Sep 20, 2026: classroom codes and a playground

Changed
Classroom codes moved out of git into Workers KV, Cloudflare’s key-value store. Each code lists its modules, a label and an optional expiry, and one command-line tool issues, lists or revokes codes without a redeploy.
A LiveCodes playground went up on its own origin, play.hellowattson.ca. Student code runs entirely in the browser and saves to the device.

Jul 10, 2026: Astro 6 and a public catalogue

Problem
Our plan called for auto-graded quizzes, interactive lesson widgets and a public catalogue, which Astro handles better.
Changed
The site moved from Eleventy to Astro 6, keeping every existing URL; moving first meant building the catalogue and track templates once. A Cloudflare Worker in front checks the access code on the server before any lesson leaves.
Result
The catalogue and undated tracks let a teacher outside our program preview a module and run it on their own schedule. A plain-language privacy page went up with them.

Mar 9, 2026: a notes site

Problem
I wanted students to have notes they could reach outside camps and classes if they wanted to keep studying, and to give instructors more resources to point students to.
Changed
It started as an Eleventy site, a static site generator, holding notes our own instructors projected in class.

What’s next (planned)

Club logins come first: club members sign in to save a session’s work to our gallery and load it again at home. They work on staging and launch after a privacy review. The rest is not built yet. In order: a teacher layer, with a “For teachers” section per module, teacher downloads scoped to the module a code unlocks, and free preview lessons; self-check quizzes that grade in the browser and store nothing; JupyterLite notebooks for Python; and simulator embeds for the hardware modules.

Constraints

A classroom is thirty devices sharing one school IP address, often on slow wifi, with no time to install anything. Classroom students cannot have accounts. Program pages label themselves upcoming, running, or finished, and those labels have to be right on a morning when nobody has touched the site in weeks.

The no-accounts rule for classrooms is also what lets the site reach outside our own rooms. BC public schools work under FIPPA, the provincial privacy law, and a tool that stores student personal information brings privacy-impact paperwork before a teacher can use it. A site that stores nothing about students gives a district privacy officer one page to read instead of a review. Accounts would give us saved progress and a class view for teachers. They would also make us the keeper of a directory of children. In a classroom the unit of access is a code, and the student stays anonymous to us. Our own clubs are where we take on accounts, because there a login controls who gets into each club and lets members take their work home.

Architecture

The Worker runs ahead of the files it serves, so a gated lesson is never handed out and then hidden. A build served without the Worker would give everything away, which is why every deploy goes through it. The rate limit counts only failed code attempts, so one student mistyping cannot lock out the classmates sharing that school IP address. The playground is a separate Worker with no gate and no secrets, and a first-party subdomain is less likely to be blocked by a school content filter than a third-party domain. Stack: Astro on Cloudflare Workers, hand-written CSS, no client-side framework.
